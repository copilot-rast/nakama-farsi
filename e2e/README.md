# End-to-end suite

Playwright specs that drive the real console overlay and the Star Catcher sample (`samples/stargame`) against a running server. Every phase adds specs here and runs the whole suite before it is reported done.

## Run

```sh
cd e2e
export PATH=~/.nvm/versions/node/v22.18.0/bin:$PATH
npm ci                 # once; browsers are not downloaded, the system Chrome is used
npm test               # everything
npm run test:console   # console specs only
npm run test:game      # game specs only
npm run report         # open the HTML report from the last run (e2e/playwright-report)
```

One spec or one test: `npx playwright test specs/console/03-economy.spec.ts -g "gift codes"`.

## How it is built

- `specs/global.setup.ts` (project `setup`) backs up the shared config rows into the schema `zz_e2e_backup` (`sql/backup.sql`), records their hashes (`sql/snapshot.sql`), marks a `pending` setup as completed so the wizard does not cover other specs, and signs in once. The session is saved to `.auth/admin.json` and injected into every console page.
- `specs/global.teardown.ts` (project `teardown`, runs after everything) fails when a spec changed config without restoring it or left `e2e_…` rows behind, then restores the backup (`sql/restore.sql`), checks the hashes match the start exactly, removes leftovers (`sql/cleanup.sql`) and drops the backup schema. If a run is killed, the next setup restores the old backup first.
- Specs that must change shared config (payment methods, providers, languages, brand, setup state) call `restoreConfig()` from `lib/db.ts` when they finish. Everything else creates its own rows with unique keys (`uid()` → `e2e_<time><rand>`, device ids `e2e-…`, test languages `xa-…`) through the console API and deletes them afterwards. Test players are deleted through the console API; their payments stay as history.
- Sandbox is never turned off. The publication spec refuses to run if any active SMS/email provider is live. The SMS login specs refuse to run unless SMS login is on and in sandbox; they read the code from the server log (`lib/accounts.ts` `waitCode`), use numbers `+98999…` (`testPhone()`), clear the `otp:` rate-limit counters before sending, and delete their phone accounts and code rows afterwards.
- One worker, one browser per test. This Mac's headless Chrome crashes (SIGSEGV) as soon as any page or context is closed, which also breaks Playwright's `storageState` loading. `lib/fixtures.ts` therefore launches a fresh Chrome for each test (`page`) and for each extra page (`spawn()`), never closes pages, and closes the whole browser at the end. Do not use the built-in `browser` fixture or `context.close()`.
- Every page fails its test on an uncaught page error.
- The updates spec never calls the real GitHub. Playwright's `webServer` starts `fake-github/server.mjs` on `127.0.0.1:7489` (or reuses one that is already running) and stops it after the run; the spec sets its scenario (commits ahead, 429, 500) through `POST /__fake/scenario` and reads the call counts (including 304 answers) from `GET /__fake/scenario`. The local server is started with `BASE_UPDATES_API_URL=http://127.0.0.1:7489` (`.local/run.sh`), so outside a test run its update check shows a connection error.
- Bank payments return to `ECONOMY_WEB_REDIRECT_URL`; on this Mac that is a static server on `:7470` that is not running, so the ZarinPal test maps that redirect to `GAME_URL` with the same query. Gateway tests skip with a reason when the sandbox host is unreachable.

## Multi-node cluster suite (phase 6)

`cluster/` is a separate Playwright project that starts four cluster nodes of `.local/cluster/nakama` as plain processes and drives them with `@heroiclabs/nakama-js` from Node (no browser). It does not touch the single node on 7450.

```sh
cd e2e
npx playwright test -c cluster/playwright.config.ts
```

- Needs Redis on `127.0.0.1:6495` (`REDIS_PORT`) and the database `nakama_cluster` (`CL_DB`) on the shared Postgres, migrated with `nakama migrate up`. Keys use the prefix `nkce2e` (`CL_PREFIX`) and are deleted before the run.
- `cluster/nodes.sh start|stop|kill|status <i>…` runs node `i` with socket `76i1`, console `76i2`, cluster port `76i3` and metrics `76i4`; state and logs in `cluster/.run/n<i>/`. The runtime folder is `cluster/.run/modules`: the five built plugins (symlinked from `.local/cluster/modules`) plus the test Lua modules in `cluster/modules/` (an authoritative match handler and RPCs for match create/signal/list, notifications, stream calls, logout, ban and disconnect). Those Lua files exist only for this suite.
- Test players are device accounts named `cle2e…`; they are deleted at the start and end.
- `specs/01-four-questions.spec.ts`: the owner's four questions with players on different nodes (relayed and authoritative matches with data, signal, listing and kick; matchmaker exactly once over three rounds of 12 players on 4 nodes, party matchmaking; room and direct chat with join/leave events and history; online flags and status changes, reconnect on another node).
- `specs/02-failures.spec.ts`: `kill -9` of a node by PID (leaves, offline, `match_ended`, its matchmaker ticket gone, players reconnect elsewhere, the node rejoins), logout and ban across nodes, live notifications and runtime stream join/send/kick/disconnect across nodes, a phase 3 suspension from the console on one node kicking the player on another, and the live support chat long-poll woken by a message on another node.
- Load: `cluster/load/` (k6 `load.js`, `run.sh`, `sample.sh`, `summ.py`, latency `probe.mjs`, `ghosts.sh` for presences and tickets left in Redis). Results are in `docs/cluster-results.md`.

## Adding specs for a new phase

1. Put console journeys in `specs/console/NN-<phase>.spec.ts`, game journeys in `specs/game/`. Import `test`/`expect` from `lib/fixtures.ts`.
2. Use `open(page, '#/…')`/`go()`/`openSettings(page, section)` and the helpers in `lib/console.ts` (`root` is the project settings body while the window is open, else `#economy-root`; `settlePanel`, `fillTranslated`, `pickRef`, `savePanel`, `search`, `rows`, `toasts`), `lib/game.ts` for the game and `lib/api.ts` for setup and checks through the APIs.
3. Create data with `uid()` keys and delete it in `afterAll`. Chat specs use rooms named `e2e-…` and delete their reports and messages afterwards (`base_chat_report.channel_label`, `message.stream_label`); `base_chat_word`, `base_report_title`, `economy_event_settings`, `base_support_settings`, `base_support_department`, `base_support_canned`, `base_config_key` (with `base_config_history` restored too), `economy_referral_settings` `base_updates_settings` (with `base_updates_state` restored too), `trophy_settings`, `clan_settings` and `clan_level` are backed up and hashed like the other shared config tables; support departments, canned replies and config keys with `e2e` keys are counted as leftovers; tickets, chats, uploads, activity and referrals of test players go with the players; event types, rules, meta rules, level tables, streaks (with their milestones), tasks, task groups, items, achievements, banners, banner placements, sponsors, chance games, prize groups, games (with their matches), automatic notification rules and notification categories with `e2e` keys are counted as leftovers and removed by the cleanup (owned items, player achievements, item request rows, chance plays and turn rows, banner and sponsor counter rows, push devices, notification choices and automatic notification hits of deleted players too). If the phase adds a new shared config table, add it to `sql/backup.sql`, `sql/restore.sql` and `sql/snapshot.sql`; if it adds new keyed rows, add them to `sql/leftovers.sql` and `sql/cleanup.sql`.
4. Assert what a user sees (text, state, numbers in the page), then cross-check through the API.
5. Run `npm test` twice in a row before reporting.

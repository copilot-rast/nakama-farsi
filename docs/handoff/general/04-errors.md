بدنهٔ هر خطا `{ code, message }` است. `code` کد وضعیت gRPC است (مثلاً ۳ ورودی نادرست، ۵ پیدا نشد، ۷ اجازه نیست، ۱۶ نشست نامعتبر).

برای بیشتر RPCها `message` خودش یک JSON است:

```json
{
  "code": "PAYMENT_IN_PROGRESS",
  "status": 409,
  "message": "متن آماده برای بازیکن",
  "meta": {},
  "retryAfterSeconds": 30,
  "field": "productId"
}
```

| فیلد | یعنی |
| --- | --- |
| `code` | کد خطا. اپ با این تصمیم می‌گیرد |
| `status` | وضعیت شبیه HTTP |
| `message` | متن ترجمه‌شده برای بازیکن، اگر سرور فرستاده باشد |
| `meta` | داده‌های بیشتر، مثلاً زمان پایان یک محدودیت |
| `retryAfterSeconds` | اگر آمد، تا این مدت دوباره امتحان نکنید |
| `field` | فیلدی از درخواست که مشکل دارد |

## قاعده‌ها

* تصمیم را با `code` بگیرید، نه با متن.
* بعد از هر خطا، وضعیت را دوباره از سرور بخوانید. فرض نکنید چیزی عوض نشده است.
* روی سوکت هم همین JSON در پیام خطا می‌آید. اپ باید هر دو شکل را با یک تابع بخواند.
* اگر `message` JSON نبود، همان رشته خود کد خطاست.

## چند کد پرداخت که همه جا یکسان‌اند

| کد | یعنی | کار اپ |
| --- | --- | --- |
| `PAYMENT_IN_PROGRESS` | برای همین محصول یک پرداخت باز هست | همان پرداخت را ادامه دهید یا وضعیتش را بخوانید |
| `PAYMENT_EXPIRED` | پرداخت منقضی شده است | یک پرداخت تازه شروع کنید |
| `STORE_MODE_CHANGED` | فروشگاه در حالت آزمایشی است؛ پرداخت بعداً بررسی می‌شود | به بازیکن بگویید خریدش ثبت شده و بعداً بررسی می‌شود |

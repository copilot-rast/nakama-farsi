# Roadmap (agreed 2026-11-10)

Order is fixed. Each phase is verified end to end with the stargame sample. Commits stay local (no push) until the owner asks. The console uses the Spatial look (phase D) from 2026-11-10; `?spatial=0` turns it off.

| Phase | Scope |
|---|---|
| 0 | Branding + first-login setup wizard (done) |
| 0b | Cluster readiness (runs right after phase 0, before phase 1): audit every plugin for single-node assumptions and fix them now so the cluster phase needs no rework: uploads behind a storage interface (local disk default, S3/MinIO option), background workers safe on many nodes (claims with SKIP LOCKED or a lease, never double-run), no in-memory state that must be shared (caches get a short TTL or DB-backed invalidation, rate limits in the DB), config only from env. From now on every phase follows these rules. Database stays as it is. Done 2026-11-10: audit, rules and results in `docs/cluster-readiness.md`. |
| 1 | Project settings window like the asp dashboard: one large window with a section list (brand, setup, languages, categories, tags, payment gateways, SMS, email, and later sections), opened from the top bar and the sidebar, deep-linkable, sections gated by admin ACL. Existing settings tabs and the «عمومی» sidebar section move into it; Nakama's own settings stay. Categories and tags follow asp: key type per item, pickers filtered by key type (+ `general` for tags), a «+» quick-create next to every picker, new key type `user` for player tags. Done 2026-11-10: `#/project-settings/<section>`, details in `docs/base/spec.md` (Console pages). |
| D | Spatial redesign of the whole console (done 2026-11-10): third overlay `console/ui/spatial` (sky, glass windows, floating rail and top bar, motion) over every native and overlay page, contrast ≥ 4.5:1 measured per page in both themes, phone layout, e2e 09–11. Details in `docs/design/spatial*.md`. |
| 2 | Accounts: phone + SMS OTP login on the existing SMS providers (rate limits, sandbox shows the code in the log), account rules (username/password length), app versions per platform with forced update and store links + client RPC, countries with flags. Done 2026-11-10: OTP in the publication plugin (hashed codes, database limits, link a guest or create an account, `loginKey` for silent sign-in), rules enforced by before-hooks in base, app versions and 243 seeded countries in base, four project settings sections (countries, account rules, SMS login, app versions), Star Catcher account screen + version check, e2e 12 and 13. Details in `docs/base/spec.md` (Accounts) and `docs/publication/spec.md` (Phone login). |
| 3 | Players and chat: player tags (and targeting notifications/offers by tag), temporary suspension with end date and a message shown to the player, chat moderation (Persian-aware word filter, message reports with report titles, temporary mute, review page). Done 2026-11-11: player tags on the native player page and in bulk, public tags readable by the player, notification target and product audience by tag; suspensions, mutes and warnings with a translated message and end time (sign-in, refresh, phone login and chat refused with a JSON notice, live kick, history, early lift, ends on time without a timer, expiry under a lease); Persian-aware word filter (`internal/chatfilter`) with mask/block/flag; player reports with seeded translatable reasons and a review page; hooks composed through `internal/hookchain`; new console section «بازیکنان و گفتگو» and settings section «عنوان‌های گزارش»; Star Catcher chat room, reporting, mute/suspension screens, own public tags and a VIP pack; e2e 15 and 16. Details in `docs/base/spec.md` (Players and chat). |
| 4 | Events and economy phase 2: player event tracking, event → prize rules, meta rules, streaks. Done 2026-11-11: admin-defined event types (built-in `login`, `purchase_completed`, `gift_redeemed`, `level_up`), client RPC with range checks and per-player limits in the database, server recording from any plugin through `internal/playerevents`, totals per player and day, raw log with retention under a lease; event prizes (count, sum or highest value; all time, per day or per week in the configured zone; once, once per window or every N; caps, player tags, date window; automatic or claimed), meta rules and level tables with prizes, daily streaks with grace days, reset or step back, 7-day cycles and claims; one claims table so no grant is doubled on any node; console pages in the economy section, project settings «رویدادها», player progress card; Star Catcher level card, daily sign-in reward panel, rewards screen and golden-star events with seeded rules; e2e 17 and 18. Details in `docs/economy/spec.md` (Events, levels and streaks). |
| 5 | Support and growth: tickets, departments, canned replies, live support chat; referral codes with economy rewards; remote content/config; player activity log. Done 2026-11-11: tickets ported from asp (departments with first-answer hours and automatic sharing, priorities, statuses, assignment, translated canned replies, internal notes, SLA times, rating, auto-close under a lease) with private signed attachments in the object store and the player notified live and in the publication inbox; live support chat with a queue, take/transfer/close (or turn into a ticket), typing and online state kept in the database (players get Nakama notifications, agents long-poll); referral codes with new-account window, self/cycle/device/phone rules, suspicious flags and held referrals, rewards for both sides after an event goal through the one claims table; remote config with typed and translated values, rules by platform, app version, player tag, country and stable percent buckets, history and rollback; one activity timeline per player written by every plugin with retention under a lease; new console section «پشتیبانی» (`ACCOUNT_NOTES`, so agents need no economy access), «فعالیت بازیکنان», «کدهای معرف», «پیکربندی بازی», three support settings sections and «قوانین معرف», player activity card; Star Catcher support, ticket and live chat screens, «کد معرف», config banner and golden-rush switch, «فعالیت من»; e2e 19–22. Details in `docs/base/spec.md` (Support, remote config and player activity) and `docs/economy/spec.md` (Referral codes). |
| 6 | Cluster (owner's choice 2026-11-11, after the spike in `docs/cluster-spike.md`): do not port nakama-plus's replication layer (lossy, does not scale past ~30k players). Take only its routing ideas: node id inside presence and match ids, send only to the node that hosts the recipient, ask the host node for remote match and party calls, memberlist or Kubernetes endpoints for membership. Build the rest ourselves on a shared Redis: presence and status, matchmaker pools, logout/ban broadcast, cross-node messages over long-lived gRPC streams, leave and match-ended events when a node dies, schedulers under the `clusterkit` lease. Keep the official module path and heroiclabs/nakama-common. Start with a k6 load test of one node, then multi-node e2e. Main Postgres untouched. |

Out of scope (asp-specific): Workspace, Partner, SdkRegistry, Type, ModuleLink. Backups belong to the server/Dokploy, not the console.

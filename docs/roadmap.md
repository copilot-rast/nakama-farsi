Order is fixed. Each phase is verified end to end with the stargame sample. Commits stay local (no push) until the owner asks. The console uses the Plane look (`console/ui/plane`) from 2026-11-12; the Spatial overlay was removed.

| 0b | Cluster readiness (runs right after phase 0, before phase 1): audit every plugin for single-node assumptions and fix them now so the cluster phase needs no rework: uploads behind a storage interface (local disk default, S3/MinIO option), background workers safe on many nodes (claims with SKIP LOCKED or a lease, never double-run), no in-memory state that must be shared (caches get a short TTL or DB-backed invalidation, rate limits in the DB), config only from env. | 6 | Cluster (owner's choice 2026-11-11, after the spike in `docs/cluster-spike.md`): do not port nakama-plus's replication layer (lossy, does not scale past ~30k players). Take only its routing ideas: node id inside presence and match ids, send only to the node that hosts the recipient, ask the host node for remote match and party calls, memberlist or Kubernetes endpoints for membership. Build the rest ourselves on a shared Redis: presence and status, matchmaker pools, logout/ban broadcast, cross-node messages over long-lived gRPC streams, leave and match-ended events when a node dies, schedulers under the `clusterkit` lease. Keep the official module path and heroiclabs/nakama-common. Start with a k6 load test of one node, then multi-node e2e. Main Postgres untouched. Done 2026-11-11 (branch `feature/cluster`, merged into `dev` locally): `cluster.enabled` (off by default; a single node is unchanged) turns on a Redis node registry with 1 s heartbeats and 5 s death detection, two long-lived gRPC connections per node pair (batched frames + calls), presence/status in Redis with per-node views of only the streams a node takes part in, routing to the node in each presence/session/match ID, host routing for authoritative matches and parties, a sharded matchmaker with fenced commits (each ticket matched once, also across failover), logout/ban/suspension through a Redis invalidation log, live notifications and the support chat signal across nodes, leave and `match_ended` events when a node dies, leaderboard/tournament callbacks once per cluster under the `clusterkit` lease; optional `redis` service and cluster env in Compose, Kubernetes notes. One node of this fork carries about 10k players of the test workload (15k: chat p95 6.9 s); 4 nodes carried 15k with chat p95 7 ms, every player online on every node, 0 ghosts, 0 double matches (nakama-plus failed at 5–10k). Multi-node suite `e2e/cluster` (9 checks incl. `kill -9`). Details: `docs/cluster-design.md`, `docs/cluster-results.md`. |

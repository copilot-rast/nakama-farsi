# Native migration and deployment notes

## Account restriction rollout (2026-10-23)

Apply all 32 Jazebe migrations, ending with `20261023190000-jazebe-account-restriction.sql`, before loading the current native module. That migration adds core-ban provenance and a durable pending local-session-revocation marker. Operator suspend/unsuspend/reactivate are restricted to the existing operator allowlists; an ordinary operator cannot target a super operator, and no operator can target their own account. The default `JAZEBE_ACCOUNT_REVOCATION_WORKER_ENABLED=false` starts no retry loop. Set it to `true` only after the migration to retry pending local token and socket revocations once a minute; any other value fails module initialization. The operator can also invoke `jazebe_operator_user_revocation_retry` with a target `userId`. Monitor `jazebe_user_account.session_revocation_pending` and the Nakama logs. All Jazebe RPCs now query authoritative account/core-ban state on every call. This adds one indexed user/account read per RPC and does not enforce state on native Nakama endpoints. Multi-node session invalidation, source SMS notification, PostgreSQL execution and live runtime behavior remain unverified; do not roll this out as a fully enforced cross-node account restriction until those gaps are closed.

## Current progression event deployment (2026-10-22)

Apply `20261023100000-jazebe-progression-events.sql` before serving Jazebe purchases or group joins with this plugin version. These transactions persist an event row before commit, then immediately attempt XP processing. Set `JAZEBE_PROGRESSION_WORKER_ENABLED=true` after migration to retry pending rows every minute following a process exit or transient database failure. Leave it unset or `false` to disable the worker; any other value prevents module registration. Event row locks and the XP uniqueness constraint prevent duplicate XP. Monitor Nakama logs and pending rows in `jazebe_progression_event`. This SQL and worker have not been tested against a live PostgreSQL server here.

`20261023110000-jazebe-medals.sql` adds the medal library, planet selections and append-only acquisitions. `20261023120000-jazebe-platform-policy.sql` adds the singleton policy with source defaults. Apply these in order through Nakama's migration command before using the corresponding RPCs. Leave `JAZEBE_MANAGERIAL_OPERATOR_USER_IDS` unset to deny platform policy writes except for actors also listed in the super-operator and base operator allowlists. The value is a comma-separated list of Nakama user UUIDs. No live SQL migration or rollback experiment has run in this workspace.

## Historical checkpoint (superseded by the execution state)

Nine additive migrations now end at `20261022200000-jazebe-mission-codes.sql`; 37 native RPCs are registered. Planet approval and media/code mission action paths are registered. Mission reward completion, wallet credit, XP, statistics and first-activity membership use one SQL transaction. The per-planet Jazebe point wallet is separate from Nakama's standard wallet because Nakama's wallet API cannot join that SQL transaction. `jazebe_wallet_summary` and `jazebe_wallet_transactions` read the Jazebe balance and ordered ledger.

`jazebe_wallet_adjust` is disabled unless the caller's Nakama UUID appears in `JAZEBE_OPERATOR_USER_IDS`; amounts above 10,000 also require `JAZEBE_SUPER_OPERATOR_USER_IDS`. Both are comma-separated allowlists and should be unset by default. The adjustment requires an idempotency key and reason, checks overdrafts, and writes audit transactionally. Jazebe's adjustment notification has not been ported. No live PostgreSQL execution or plugin load has been verified, so these paths are not yet production-verified.

### Earlier deployment notes (historical)

Seven migrations, ending in `20261022180000-jazebe-brand-team.sql`, join Nakama's existing embedded migration sequence. The existing `nakama migrate up` command applies them before startup. They create Jazebe tables, membership provenance, fan counters, draft lifecycle fields, categories, planet settings, mission definitions, audit records and brand roles; existing Nakama tables are unchanged. Existing active planets stay active; old `disabled` planets become `suspended`. Existing brand owners receive owner/main admin records during migration. Back up the database before upgrading. The down migrations retain Jazebe data because automated deletion would erase user records.

`build/Dockerfile.local` compiles the native Go runtime module with Nakama's Go toolchain and vendor tree, then copies `jazebe.so` to `/nakama/data/modules`. `docker-compose.yml` builds this Dockerfile. It runs PostgreSQL (`postgres`), and its one-shot `nakama-migrate` service applies migrations before Nakama starts; see `database-configuration.md`. No Redis service is added. The reconciliation executable is not started by Compose; schedule it separately after database migration.

Authenticated clients call the native Jazebe RPCs through Nakama's normal RPC API. Planet creation requires brand ID, name and slug; it returns a `setup` draft and creates default settings transactionally. Brand creation requires `name` and `ownerUserId`, and is denied unless the caller's Nakama UUID appears in the comma-separated `JAZEBE_OPERATOR_USER_IDS` server environment variable. Leave that variable unset to disable privileged operator actions. Creation writes owner/main admin records. Brand planet list/detail/update are still owner-scoped; source technical-admin write permissions are pending. Publish check/request/withdraw use the source requirements, including an active mission definition. Four operator lifecycle RPCs are allowlisted and write audit records; approval is withheld until mission actions and rewards work. Media mission creation currently supports a validated draft of the `media_view` type only. Join returns whether membership was newly created and its original path and time.

Build the fan counter worker from the repository root with `go build -o jazebe-reconcile.exe ./integrations/jazebe/reconcile`. Set `JAZEBE_DATABASE_URL` to the same PostgreSQL database used by Nakama and run the executable once per day at 04:00 in the deployment timezone. It locks its `jazebe_xact_lock` row with `FOR UPDATE NOWAIT` (PostgreSQL and CockroachDB), updates only counters that differ, logs the count corrected, and exits. Live execution has not yet been verified. Keep the database URL in a deployment secret.

The original Jazebe app and worker are not deployed. Their remaining behavior requires native ports; 18 partial RPCs and one isolated worker do not establish full parity. Mission activation, member action, completion and reward paths remain unimplemented, so a mission definition should not be treated as a usable mission. Live PostgreSQL migration and plugin loading remain unverified.
